# effort-router

Claude Code mod（関数フックのプラグイン）。版 0.7.0、Claude Code 2.1.289 で作成（0.4.0〜0.7.0 は 2.1.291 で更新）。

## 概要

**Claude Opus / Sonnet 5.5 以降と Fable / Mythos 5.1 以降**を対象にした mod です（判定基準は Opus 5.5 に合わせています）。プロンプトごとに、メインスレッドの effort（推論の深さ）を **low / medium / high / xhigh** から自動で選びます。速度、コスト、精度のつり合いを取るのが目的です。

- 判定には Haiku の `$.model.classify` を使い、今回の依頼に加えて、前のターンの様子（信号と短い抜粋）も渡します。
- 判定の軸は**作業の量ではなく、正しい答えがどれだけ不確かか、見落としたときの損がどれだけ大きいか**です（基準は下の「判定基準」）。max は選びません。
- 判定結果はそのまま使います（上げるのも下げるのも即座）。判定が低すぎた場合は、**ターンの途中で1段上げて**補います（往復が10回を超えたとき、またはツールのエラーが2回出たとき。1回の判定につき1段まで）。
- 前の回答で示した選択肢を `2` や `3で` のように番号で選んだときは、**選んだ選択肢の本文**で判定します。
- 「はい」「OK」のような短い返事は、前の回答が質問や提案で終わっていれば、その内容で判定します。
- `AskUserQuestion` で回答したときは、ターンの途中でも、選んだ選択肢（label と description）で判定し直します。**回答の次のリクエストから**、ターンの残りをその段階で進めます。
- バックグラウンド作業の完了通知（`<task-notification>`）は、ユーザーの依頼ではないので判定せず、前のターンの段階を引き継ぎます。
- **モデルは変えません。** モデルの振り分けは、サブエージェントの定義（`~/.claude/agents/`）に任せます。
- 組み込みの `/effort` で変えたときは、**その場でステータスラインに反映し、そのターン（ターンの合間なら次のターン）を設定どおりの effort で動かします**。固定はしないので、その次のプロンプトからは通常どおり判定します。
- 対象外のモデル（Opus 5 以前、Sonnet 5 以前、Fable 5、Haiku など）、サブエージェントのリクエスト、effort を受け付けないモデルは書き換えません。対象を「effort を変えてもプロンプトキャッシュが保たれるモデル」（Claude Code の公式ドキュメント）に絞っているのは、それ以外では切り替えのたびにキャッシュが作り直されて費用が増えるためです。

### 判定基準

| 段階 | 対象 |
|---|---|
| low | 見落としの余地がない作業。雑談、確認、お礼、翻訳、コミット、手順がすべて決まっている機械的な修正（誤字、リネーム、移動） |
| medium | 方針が決まっている普通の作業。決めた方針や設計の実装、テストの追加、コードの説明、調べもの |
| high | 正しい答えが不確かな作業。不具合の原因調査、設計案の比較、差分のレビュー、あいまいな要件の整理 |
| xhigh | 難しく、見落としの損が大きい作業。コードベース全体のレビューや監査、プロジェクト全体からの該当箇所の洗い出し、全体にわたる移行、抜本的な設計の見直し、直したのに直らない不具合、並行処理・セキュリティ・データ消失に関わる作業、長時間の自律作業 |

基準の根拠（2026-10-07 時点の調査）:

- Opus 5.5 の既定は medium で、公式は「medium から始めて、xhigh と max は効果を測った作業にだけ使う」としています。medium は Opus 5 の high を上回るとされています。
- 公式の用途表では、xhigh は長時間のエージェント作業やコーディング作業向けです。
- 第三者の総合評価（Artificial Analysis、又聞き）は low 42、medium 51、high 54、xhigh 56、max 58 点です。上の段階ほど伸びが小さく、費用は増えます。max は過剰に考えて品質が下がる報告があります。
- 「effort を上げると抜け漏れが減る」ことを直接測ったデータは見つかりませんでした。xhigh の「広さ」の項目（全体レビュー、洗い出し）は、実測のない仮説です。

## 導入

Claude Code で次のコマンドを実行します。

```
/plugin install effort-router --marketplace nextscape/ns-mods
```

新しいセッションを開くと読み込まれます。

- 前提: メインのモデルが Claude Opus / Sonnet 5.5 以降、または Fable / Mythos 5.1 以降であること。ほかのモデルでは effort を書き換えません。
- 確認した Claude Code の版: 2.1.291
- mod の API は早期アクセス版のため、Claude Code の版が変わると動かなくなることがあります。

## 使い方

| コマンド | 動作 |
|---|---|
| `/effort-router` | 現在の状態（on / off）を表示する |
| `/effort-router on` | 自動判定を有効にする（既定） |
| `/effort-router off` | 自動判定をやめる。組み込みの `/effort` の設定がそのまま効く |
| `/effort-router log` | 段階ごとのターン数と平均所要時間、直近10件の判定を表示する |
| `/effort-router eval` | 評価セットを実際の Haiku で判定し、一致数と低すぎる判定の数を表示する |

- on / off は `$.store` に保存され、次のセッションにも引き継がれます。
- 組み込みの `/effort` で変えると、そのターン（ターンの合間なら次のターン）だけ設定どおりに動き、その後は自動判定に戻ります。ずっと固定したいときは、`/effort-router off` にしてから `/effort` を使ってください。
- 組み込みの `/effort medium` のように段階名を付けて実行すると、その段階が以後のセッションの既定として保存されます。このセッションだけ変えたいときは、`/effort` のスライダーで `s` を押します（[公式ドキュメント](https://code.claude.com/docs/en/model-config.md)）。
- 組み込みの `/effort auto` は自動判定ではありません。保存した段階を消して、モデル既定の段階に戻すだけです。たとえば Opus 5.5 の既定は medium です。

### ステータスライン

エンジンが先頭に `effort-router:` を付けて表示します。

| 表示 | 意味 |
|---|---|
| `on, waiting for the first prompt` | 有効だが、まだ判定していない |
| `high` | 判定の結果、high で実行している |
| `low (choice 3)` | 前の回答の選択肢 3 が選ばれたので、その本文で判定した |
| `high (reply to question)` | 前の回答の質問への短い返事として判定した |
| `xhigh → medium (asked: 進め方)` | ターンの途中で `AskUserQuestion`（見出し「進め方」）に回答したので、判定し直して xhigh から medium に変えた |
| `medium → high (raised after 10 requests)` / `(raised after 2 tool errors)` | ターンが長引いたか、エラーが続いたので、途中で1段上げた |
| `high (task notice, kept)` | バックグラウンド作業の完了通知なので、前ターンの段階を引き継いでいる |
| `high (set by /effort)` | `/effort` で high に変えた。そのターン（ターンの合間なら次のターン）は設定どおりに動く |
| `changed (set by /effort)` | スライダーで変えたため、値がまだ分からない。次のリクエストで実際の値に置き換わる |
| `high (short prompt, kept)` | 短い入力で、前の回答が質問や選択肢で終わっていないので、前ターンの段階を引き継いでいる |
| `high (unsure, kept)` / `high (error, kept)` | 判定がどのラベルにも当てはまらなかったか、失敗したため、前ターンの段階を引き継いでいる |
| `xhigh (session effort, …)` | mod は書き換えず、セッション本来の effort で実行している |
| `off (/effort applies)` | 無効 |

## 仕組み

### 判定の流れ

```
turn.start
 ├ 直前のリクエストが対象外のモデル → 判定しない
 ├ ターンの合間に /effort を実行していた → 判定せず、セッションの effort（設定どおり）で動かす
 ├ バックグラウンド作業の完了通知 → 前ターンの段階を引き継ぐ（判定は呼ばない）
 ├ 前の回答の選択肢を番号で選んだ（"2" "3で" "1と3でお願いします"）
 │            → classify([rubric] + [choice] + … + [selected] 選択肢の本文)
 ├ 入力が20文字未満で、前の回答が質問か選択肢で終わっている
 │            → classify([rubric] + [reply] + 前ターンの信号と抜粋 + 今回の返事)
 ├ 入力が20文字未満で、上のどちらでもない → 前ターンの段階を引き継ぐ（判定は呼ばない。最初のターンならセッション本来の effort）
 └ それ以外 → classify([rubric] + 前ターンの信号と抜粋 + 今回の依頼)
 （判定結果をそのまま使う。判定に失敗したか、どのラベルにも当てはまらなければ前ターンの段階）
turn.step     → Opus 5.5 のメインスレッドのリクエストの effort を書き換え、往復回数を数える
                判定から往復が10回を超えたか、ツールのエラーが2回出たら1段上げる（1回の判定につき1段まで。上限 xhigh）
tool.call     → ツール呼び出し数とエラー数を数える
 └ AskUserQuestion の回答（メインスレッドのみ）
              → classify([rubric] + [choice] か [reply] + 今のターンの信号と質問文 + 回答 + [selected] label — description)
                -> 次の turn.step から、ターンの残りをその段階で送る（途中の引き上げはここから数え直す。判定に失敗したら変えない）
turn.complete → 回答の全文から選択肢と「質問で終わったか」を抜き出し、次のターン用の信号として $.state に保存する。ログを $.store に追記する
```

### 判定に渡す入力

会話履歴は読みません。mod が自分で集めた値だけを渡すので、会話が長くなっても入力量は一定です。

```
[rubric] 4段階の判定基準（固定）
[prev] effort=xhigh steps=9 tools=14 tool_errors=2 dur=210s max3=xhigh
[prev_request] 前ターンの依頼の冒頭100文字
[prev_answer_tail] 前ターンの回答の末尾300文字
[request chars=1234] 今回の依頼の冒頭600文字 … 末尾200文字
[selected] 3: 選んだ選択肢の本文（番号で選んだときだけ）
```

番号で選んだときは `[choice]`、短い返事のときは `[reply]` の判定規則を `[rubric]` の直後に足します。この2つを `[rubric]` 本体に常に入れると、普通の依頼まで低めに判定されるようになりました（評価セットで既存の16件のうち4件が LOW）。そのため、該当するときだけ足しています。

### 選択肢の読み取り

- 回答の全文から、行頭の `1.` `1)` `(1)` `①` `１．` `A.` `案1:` と、表の行 `| 1 | … |` を拾い、最後のひと続き（`1` か `a` で始まり直す）を選択肢として保存します。1件150文字、最大10件までです。
- 入力から番号と「で」「番」「お願いします」などの言葉を取り除いて何も残らなければ、選択とみなします。保存した選択肢にない番号が含まれていれば選択とはみなしません。
- `2で、テストも追加して` のように番号以外の指示が付くと選択とはみなさず、20文字未満なら短い返事として判定します。

- コードブロックは `[code: ts 40 lines]` に、スタックトレースは `[stack trace: 25 lines]` に置き換えます。トークン数を減らしつつ、コードやエラーを含むという信号は残します。
- 入力は最大でも1回あたり1,000トークン程度の見込みです（日本語のトークン数を経験則から見積もった値で、実測ではありません）。判定1回の応答時間は、実測で約0.7〜1.1秒でした。

### classify のラベルは1語にする

ラベルは `low` / `medium` / `high` / `xhigh` の1語で、判定基準は入力の冒頭の `[rubric]` に書いています。最初はラベルに定義文を入れていました。しかし Haiku は長いラベル文を言い換えて返すため、完全一致の照合に失敗し、評価セットで 0/16 になりました。ラベルを1語に変え、判定基準を具体的にした結果、2回続けて 16/16 になりました。

### 状態とログ

| 保存先 | キー | 内容 | 有効範囲 |
|---|---|---|---|
| `$.state` | `prev` / `recent` | 前ターンの信号（選択肢と「質問で終わったか」を含む）、直近3ターンの段階 | セッション内（mod を再読み込みしても残る） |
| `$.store` | `mode` | `on` / `off` | セッションをまたいで残る |
| `$.store` | `log` | 直近200ターンの判定ログ（依頼の冒頭40文字を含む） | セッションをまたいで残る（手元のみ） |

## 開発時の確認

リポジトリの直下で実行します。

```bash
claude plugin validate mods/effort-router   # マニフェストとフックの静的検査
claude plugin test mods/effort-router       # tests/*.test.ts を実行
cd mods/effort-router && npx -p typescript@5 tsc -p .   # 型検査（mod を一度読み込んで型が生成されたあと）
```

`tsconfig.json` と `.claude-plugin/types/` は、mod を読み込んだときにエンジンが生成します。手で編集しないでください。

## 判定基準を調整するときは

1. `hooks/route.ts` の `RUBRIC` を編集する。実際に誤判定した入力は `hooks/eval-cases.ts` に足す。
2. `claude plugin test` と `tsc` を通す。
3. 新しいセッションで `/effort-router eval` を実行し（実際に Haiku を31回呼ぶので、少額の費用がかかります）、一致数と `LOW`（低すぎる判定）の数を確かめる。Git Bash から `claude -p "/effort-router eval"` を実行するときは、`MSYS_NO_PATHCONV=1` を付けないと `/` 始まりの引数がパスに書き換えられる。

## 制約と既知の課題

- 判定の一致率は、評価セット31件で約90%（5回の実行で 27〜29/31）です。外れはすべて1段違い（xhigh を high、medium を low と判定するなど）で、2段以上の外れはありませんでした。低すぎる判定は、途中の引き上げで補います。
- 途中の引き上げは、往復が多いだけの作業（量は多いが単純な作業）でも1段上がります。閾値（10回、エラー2回）は仮の値で、ログを見て調整する前提です。
- `classify` には制限時間（`timeoutMs`）を付けられません。
- 番号で選んだときと短い返事のときは、0.3 まで判定を省いていたぶん、1回あたり約0.5〜1.5秒（評価セットでの実測）待ち時間が増えます。
- `AskUserQuestion` の回答のあとは、判定を待つぶん約1〜3秒（評価セットでの実測）遅れて次の処理に進みます。判定はバックグラウンドではなく同期で待ちます。
- `AskUserQuestion` で作業内容と関係の薄い質問（ファイル名の選択など）に答えても判定し直すので、effort が不要に上下することがあります。
- プロンプトキャッシュ: Claude Code の公式ドキュメントによると、Opus 5.5 では（API キーかサブスクリプションなら）effort を変えてもキャッシュは保たれます。実際のセッションの記録でも、effort が変わったリクエストでキャッシュの読み込みが続いていることを確かめました（1件）。Bedrock、Google Cloud、ゲートウェイ経由では、変えるたびにキャッシュが作り直されます。
- サブエージェントの中の `AskUserQuestion` は対象外です。ただし、この除外は結合テストでは確かめていません（テストから `agentId` を付けて呼べないため）。
- 番号付きの箇条書きが選択肢ではなく手順や変更点の一覧でも、番号で返せば選択肢として扱います（本文を見て判定するので、大きく外れることはない見込みです）。
- 評価セットの31件（0.6 で4段階の基準に合わせて期待値を付け直し、xhigh と low のケースを追加）は自作で、判定基準もそれを見ながら調整しました。実際の使い方での精度は `/effort-router log` で確かめる必要があります。
- mod の API は早期アクセス版で、Claude Code の版が変わると仕様が変わることがあります（この mod は 2.1.289 で作成しました）。
